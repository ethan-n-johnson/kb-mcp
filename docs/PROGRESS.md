## Deviations from PLAN.md

Decided while splitting the plan into phases:

1. **IMDSv2 hop limit is 2, not 1.** The app runs in a Docker bridge network and needs the instance role to read the SSM token parameter and write originals to S3. With a hop limit of 1 those calls fail. The SSRF guard in `ingest_url` (which blocks `169.254.169.254`) is the control that keeps instance credentials away from user-supplied URLs. IMDSv2 tokens are still required. (Phase 06)
2. **User data lives inline in `infra/app.yaml`**, not in a separate `infra/user-data.sh`, because CloudFormation cannot read a local file into `UserData`. (Phase 06)
3. **Container logs ship with Docker's `awslogs` log driver.** The CloudWatch agent is still installed, but only for memory and disk metrics. (Phase 15)
4. **Uploads also accept multipart files** at `POST /api/docs/file`, and chunks can be fetched at `GET /api/chunks/{id}`. These add to the REST table; they do not change it. (Phase 05)
5. **Gap resolution is automatic**: after a successful upload, unresolved gaps are re-searched against the new doc and marked resolved when the rerank score is high. (Phase 08)

6. **No ECR and no EFS (sandbox change, 2026-10-08).** The Cloud Architecting 3 sandbox denies `ecr:CreateRepository` and `elasticfilesystem:CreateFileSystem`. The image travels as `docker save | gzip` in S3 (`images/kb-mcp-<tag>.tar.gz`, `infra/push-image.sh`, loaded by the user data), and the SQLite database lives on the instance root volume (`/data/kb.db`) with a continuous snapshot to `s3://<bucket>/snapshots/kb-latest.db.gz` (`kb/snapshot.py`) and a restore at boot (`python -m kb.cli restore --latest --force --target /data/kb.db`). The recovery point becomes a few seconds instead of zero; multi-AZ is kept. Details in `docs/PLAN.md` ("Sandbox changes") and below.
7. **Root volume is gp2, 30 GB.** The sandbox allows gp2 only, up to 35 GB. Encrypted stays `true` until a real launch proves KMS (list only) allows it; the fallback is `Encrypted: false`, to be recorded here and in `docs/SECURITY_REVIEW.md`.
8. **Instance role is `myS3Role` (S3 only); no SSM, no CloudWatch Logs, no custom metrics (sandbox change, 2026-10-09).** `LabInstanceProfile` does not exist in the Cloud Architecting 3 sandbox and IAM is read only, so the launch template takes the profile name from the `InstanceProfileName` parameter (`KB_INSTANCE_PROFILE` in `deploy.sh` and `up.sh`). Of the two profiles that exist, the lab user may only pass `myS3Role`: `EMR_EC2_DefaultRole` (S3, CloudWatch metrics, `ec2:DescribeTags`) fails with "You are not authorized to use launch template", and a `run-instances --dry-run` with each profile confirmed `iam:PassRole` is the cause. `myS3Role` has one inline policy, `s3:*` on `*`. Consequences:
   - **Write tokens live in the bucket**, at `s3://<bucket>/config/write-tokens` (same `name:secret,...` format), and the app reads them itself through the instance role (`KB_TOKENS_SOURCE=s3`, `KB_TOKENS_KEY`, `kb/config.py`). The user data only checks the object exists. The SSM path stays the default for environments that allow it.
   - **Container logs stay on the instance** (Docker `local` driver, 5 files of 10 MB), which replaces deviation 3. There is no log group.
   - **Custom metrics cannot be published.** `MetricsMode=api` (the default) sends with `put_metric_data`, which `myS3Role` denies; the sender logs a warning and retries every 30 seconds without ever affecting a search. The CloudWatch agent also cannot publish. So `kb-keyword-mode`, `kb-high-latency` and `kb-memory` never get data (they stay OK or INSUFFICIENT_DATA); the ALB alarms (`kb-unhealthy-host`, `kb-no-healthy-host`, `kb-5xx`) and the SNS emails still work. Demo step 7 uses the `kb-no-healthy-host` alarm (an instance replacement) instead (PLAN.md, "Demo corpus and demo script").
   - **No Session Manager or `ssm send-command`** on the instances. When a boot fails, the EXIT trap copies `/var/log/kb-bootstrap.log` and the last 500 container log lines to `s3://<bucket>/debug/<instance-id>-<time>-*.log` before signalling.
   - Supersedes the SSM part of deviation 1: the hop limit stays 2 because the container still needs the instance role for S3.

  - **Error text.** Failures are `ToolError`s; the 2.x SDK always prefixes their text with `Error executing tool <name>: `. So the refusal reads `Error executing tool upload: This tool needs a valid write token` (the sentence is exact; the prefix only names the tool). Service errors read `<code>: <message>` (for example `not_found: doc 999 not found`); argument problems from the SDK's schema check come back as error results too; unexpected exceptions show only `Error executing tool <name>` and the traceback goes to the log.
  - **Tool arguments.** Names, defaults and optionality equal the PLAN.md table (a fast test parses the table in `docs/PLAN.md` and compares it with `tools/list`). One addition: `upload.format` defaults to `markdown` (the table lists it without a default). `get` takes `doc_id` or `chunk_id`, both optional in the schema; the service demands exactly one. `delete` and `merge` carry `destructiveHint`, read tools `readOnlyHint` (annotations are advisory).
  - **Results.** Tools return the pydantic result's `model_dump()` as a dict, the same JSON as REST (the SDK also puts it in `structuredContent` and as JSON text). `UploadResult.payload()` (new in `kb/schemas.py`) is the one place that drops nulls and defaults; `api._upload_response` uses it too. An exact `duplicate` is a normal result with `status: "duplicate"` (REST uses 409), `possible_duplicate` and `near_duplicate_check` are as in REST.
  - **Threading.** Each tool call opens its own short-lived SQLite connection inside `run_in_threadpool` and runs the token check and the service call there, so embedding, S3 and gap resolution never run on the event loop; `search` awaits `service.search` directly. The shared `SearchState` comes from `app.state.search` (looked up lazily because the lifespan creates it) or, for stdio, from `indexing.build_state` plus `indexing.start`.
  - **Stdio.** `python -m kb.cli mcp-stdio` calls `setup_logging(sys.stderr)` first and never imports `kb.main` (which configures stdout logging at import). The 2.x SDK additionally claims fd 1 for the protocol and diverts stray `print` calls while serving; a deliberate `print` before startup and stdout logging were both caught by the tests.

- **Sandbox change (S3 images and snapshots):**
  - **Where the dirty hook lives.** `kb/db.py`: `connect()` returns a `sqlite3.Connection` subclass (`_Connection`, with a `_Cursor`) that compares `total_changes` after every statement that leaves the connection outside a transaction, and calls the commit listeners when it moved. It sits on the connection, not in `db.transaction` or the service layer, because some writes run in autocommit outside any transaction (the fallback toggle's audit row, the `s3_key` update after an upload) and a hook in `db.transaction` would miss them; a mutation check (report only on `COMMIT`) failed exactly the two fallback toggle tests. `ROLLBACK` discards the pending count, `init_schema` is silent (an empty database never becomes a snapshot), reads and no-op updates are silent. `connect()` is the only way the app opens the database (`sqlite3.connect` appears in `kb/` only in `kb/backup.py`, which copies or checks files). `tests/test_snapshot.py::test_every_write_route_marks_the_database_dirty` runs 23 REST, UI and MCP write routes (including searches that log a gap) and `test_the_startup_backfill_marks_the_database_dirty` covers the backfill; `test_reads_do_not_mark_the_database_dirty` runs 15 reads; `tests/test_commit_hook.py` covers the hook itself.
  - **Snapshotter** (`kb/snapshot.py`): one daemon thread; trailing-edge debounce (it waits `KB_SNAPSHOT_INTERVAL` after the first dirty mark, then uploads once, so a burst makes one upload and the recovery point is at most interval plus upload time); a failed upload is logged (`snapshot failed`) and retried one interval later; every upload logs `snapshot uploaded` with `key`, `bytes`, `ms`, `docs`; the lifespan starts it before the backfill and stops it (final flush in a worker thread) after the MCP session manager exits and before the connection closes. Not started by `mcp-stdio` (a local stdio server with `KB_BUCKET` set must not overwrite the deployed snapshot). `app.state.snapshots` is the instance (None when off).
  - **Restore order** (`kb/backup.py`): `--latest` is the snapshot, else the newest backup, else `NothingToRestore` (CLI exit 0, "starting with an empty database"). A damaged snapshot (bad gzip, failed integrity check) falls back to the newest backup with a warning; a failed download or listing never does (it raises, exit 1, the user data retries and finally fails the boot), so a transient S3 error cannot silently restore day-old data or start empty over the real snapshot. Not in the spec: restoring a backup over the live database (`--target` equal to `KB_DB`, source not the snapshot, snapshots on) also uploads the restored file as the new snapshot, otherwise a replacement instance would restore the state the operator just undid.
  - **Infra.** `kb-data` holds only the bucket (new `images/` 30 day rule and an abort-incomplete-multipart rule); exports are now 8. `app.yaml` user data: packages, `/data` directory, `aws s3 cp ... | gunzip -c | docker load` (retried), the restore container (retried, the boot fails if it cannot read S3), `docker run --stop-timeout 30`. `HealthCheckGracePeriod` stays 600. `infra/push-image.sh` deletes a partial object when the upload fails and checks the object with `head-object`. `restore-on-instance.sh` documents that `--latest` after a bad delete restores the bad delete (use `--key backups/...`).
  - **Known gaps.** An old instance terminated by a rolling update may flush its last snapshot after the replacement has already restored (a window of seconds). The integrity check runs on every snapshot, which costs time on a large database.
